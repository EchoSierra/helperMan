## Open

- **Apply migrations to the eventual target database.** The five migrations are applied and current on the dev and test databases. Before applying them to any other target, confirm its identity and state, inventory existing legacy rows, approve a lossless classification/mapping for legacy `User` data, review/backup, and apply through the deployment process with `prisma migrate deploy`. Do not assume legacy people rows are accounts or vice versa.
- **Verify audit acceptance criteria.** Align persisted audit events with the approved minimal actor/action/target/time shape; cover authentication, MFA, account/role, report, helper, and qualification activity. Make writes and their audit events atomic, fail closed for reads if audit persistence fails, and ensure events contain no field values, PII, IP addresses, credentials, or secrets.
- **Extend PostgreSQL integration coverage.** `npm run test:integration` (separate `*_test` database) (safety: `setup-env.ts` pins `DATABASE_URL` to `TEST_DATABASE_URL` before any import and refuses names without `test`) now covers the account-administration services: creation, rollback on audit failure, disable/last-admin guard, deletion, role revoke, password and TOTP reset. Helper and qualification services are now covered too (CRUD, validation, role denial, cursor pagination, cascade). Self-service password change (TOTP check, 5-failure lockout, session revocation) is covered as well. Still to cover: audit view, migrations/constraints, retention. Test migrations and database constraints, role boundaries, qualification ownership/date handling, audited reads and writes, rollback/fail-closed behavior, and retention deletion using synthetic data only.
- **Approve no-other-Administrator recovery.** The operator break-glass script `npm run auth:recover-admin` is implemented, audited (`ADMIN_RECOVERED`), integration-tested and documented in the README; it keeps TOTP re-enrollment mandatory. Still open: the organization's approval of who may run it and how identity is verified, i.e. an approved operational procedure that preserves mandatory TOTP re-enrollment and does not grant protected access before re-enrollment.
- **Complete production operational readiness.** Obtain formal approval for both helper and audit retention schedules and record them at `/admin/retention`; schedule `npm run retention:run`; provision at least two verified Administrators with completed TOTP; verify the production preflight; and complete production migration review, encrypted backup/restore testing, TLS/private database configuration, monitoring, and deployment ownership. Production use remains blocked until the required approvals and account readiness are verified.
- **Close release security review follow-ups.** Review done: one medium finding (spoofable `X-Forwarded-For` bypassing the sign-in rate limit) fixed via `TRUSTED_PROXIES` plus a preflight blocker. Remaining recommendations: hash session tokens at rest and move rate limiting to shared storage before running multiple instances; re-review after production configuration.

## Done

- **Apply database migrations to dev and test.** All five migrations (initial schema, authentication, helper registry, audit immutability, and retention policy) are applied. `prisma migrate status` verified both configured databases are up to date. Legacy `User`/`Role`/`Permission`/`Identity`/`AuditLog` rows remain untouched; no production or other target database was changed.
- **Administrator account management.** `/admin/maintainers` supports creating a Maintainer, disable/enable, session revocation, authenticator reset, password reset, deletion, and Administrator grant/revoke (never leaving fewer than two verified Administrators); users change their own password at `/account/password`. All actions are audited and integration-tested; grant/revoke, deletion and password change are browser-confirmed. Playwright covers Administrator/Maintainer separation and immediate session revocation on disable. Not yet in e2e: password change, deletion, and grant/revoke.
- **Audit feature.** Events cover authentication/MFA/account/report/retention actions with transactional, fail-closed writes and reads (helper writes roll back if the audit event cannot be stored; sessions are deleted if their sign-in event cannot be stored). `audit_events` is append-only via a DB trigger; deletion is only possible for the retention job under `app.audit_retention`. A Maintainer-only paginated `/audit` view shows minimal actor/action/target/time metadata. A least-privilege runtime DB role (`scripts/sql/app-role.sql`) is documented and verified on the test database. Verified by integration and e2e tests. Still open: verify the role on the target database.
- **Administrator-maintained retention schedules and retention job.** `/admin/retention` records the approved inactive-helper and audit-log periods with a decision reference, approver and time (audited); the preflight now checks these records instead of env flags. `npm run retention:run` is a dry run by default, `--confirm` hard-deletes eligible inactive helpers (qualifications cascade, `HELPER_PURGED` id-only audit) or old audit events (privileged `RETENTION_DATABASE_URL`, trigger opt-in). `helpers.deactivatedAt` starts the clock. Integration- and e2e-tested; browser-confirmed. Scheduling examples (systemd/cron) are in the README. Still open: the organization actually approving periods and enabling the schedule.
- **Browser end-to-end coverage.** `npm run test:e2e` (Playwright, port 3100, `TEST_DATABASE_URL`) covers mandatory TOTP enrollment, rejected credentials, Administrator-created Maintainer creating helpers/qualifications and the expiry report, Administrator/Maintainer separation, immediate session revocation on disable, and recovery plus TOTP re-enrollment. It found and fixed a bug where framework `$ACTION_*` form entries made helper/qualification creation fail validation. Not covered: expiry-report boundary dates, password change, role grant/revoke and delete in the browser.
- **Requirements/design updated** for Maintainer deletion and self-service password change (requires current password + TOTP).

- **TOTP enrollment QR code:** the enrollment page shows a QR code in addition to the manual key (some authenticator apps reject the long manual key).
- **Manually verified in the browser:** sign-in with TOTP, password change with TOTP, and an Administrator granting themselves the Maintainer role, Administrator maintainer deletion, and the retention schedule page.

- **Authentication foundation:** Email/password sign-in, mandatory TOTP enrollment and verification, protected-route access controls, Administrator bootstrap, and production preflight are implemented.
- **Maintainer registry slice:** Maintainer-protected helper directory, profile create/update, qualification create/update, and the qualification-expiry report are implemented. The report uses the approved UTC date-window semantics and includes inactive helpers.
- **Initial validation and unit tests:** Strict helper/qualification validation, authentication policy/configuration coverage, and qualification-expiry boundary tests are present.
- **Read-only audit-log view:** Added Maintainer-protected access at `/audit`, displaying paginated actor, action, target reference, and UTC event time without fetching linked account or helper details.
- **MVP scope and key design decisions:** PostgreSQL, fixed helper profile fields, name-only directory search, UTC report boundaries, additive explicit roles, and deferred future features are recorded in `requirements.md` and `docs/TDD.md`.

## Explicitly out of this implementation plan

Helper self-service, tasks, equipment, dynamic fields, data export, missing-qualification reports, broader analytics, and a general-purpose configurable permission system are future scope, not first-delivery tasks.
